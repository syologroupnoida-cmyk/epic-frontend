# Ecommerce module

The public route is `/shop` (`src/pages/shop.js`). All shop components, catalog data and scoped styles live here. Shop artwork lives in `public/images/ecommerce/`.

`ShopHome.jsx` loads public products from GET `/shop/products` using the public Axios client (no admin token or refresh interceptors). Categories load from GET `/shop/categories`; choosing one expands nested subcategory checkboxes populated by GET `/shop/subcategories?categoryId=...`. Filters send categorySlug, subcategoryId, minPrice, maxPrice, page and limit. Price controls display INR and convert to integer paise; filter units are inferred from the product price contract and still need live confirmation. Search is limited to the current page. Changing category clears the selected subcategory and resets pagination. The API accepts one category and one subcategory at a time; unchecking a selection clears that filter. A two-thumb MUI price slider appears first in the sidebar and applies on release, with no numeric price inputs or Apply button. Its upper endpoint means any price. All returned categories appear dynamically below the banner, wrapping on smaller screens.

Cards link to `/shop/{slug}` and load GET `/shop/products/{slug}`. The detail page uses API images, variant color/size selection, paise pricing, stock and a quantity control. Missing images show a placeholder. The two columns have equal widths on desktop, with a compact gallery and an image-overlay wishlist toggle. The shared header opens API-backed wishlist and cart drawers from the right. Its Home menu points to `/shop`, the logo points to `/`, and the profile Dashboard link points to `/dashboard/shop` with existing admin access rules. My orders and Delivery addresses are available in the profile menu.

Signed-in shopping uses MainApi and the existing token-refresh interceptor. Wishlist POST/DELETE `/shop/wishlist/products/{productId}` and GET `/shop/wishlist` synchronize the heart state and header count. Cart POST `/shop/cart/items` sends only variantId and integer quantity; GET `/shop/cart` supplies drawer contents and checkout summary. The legacy browser cart/wishlist is retired and is not automatically uploaded. Guest actions require login, and the login next parameter accepts only internal shop paths. Shared account data is cleared on logout/account changes; in-flight reads from an old account are ignored. Duplicate writes are blocked, and a successful write followed by a failed read requires a refresh before another change.

Buy Now adds the selected variant to the server cart, then opens `/shop/checkout`. It reviews the entire API cart because the checkout contract supplies only addressId. GET `/shop/addresses` displays saved address cards with radio selection. Edit fills the form. Create POST `/shop/addresses` and confirmed PATCH `/shop/addresses/{addressId}` send exactly fullName, phone, line1, city, state, pincode and boolean isDefault. The form uses MUI inputs and validates a 10-digit phone and 6-digit pincode. Saving refreshes addresses and selects the saved record; a failed follow-up read requires refresh to avoid repeating the write.

Confirm checkout posts exactly `{ addressId }` to `/shop/checkout`, then opens `/shop/orders/{orderId}` when an ID is returned. Order history uses GET `/shop/orders?page=1&limit=20` at `/shop/orders`, with details loaded by GET `/shop/orders/{orderId}`. Status, payment status, items and totals come from the server; unpaid order details now include Razorpay payment selection and initiation. A checkout reservation is never treated as a successful payment. Unconfirmed checkout responses block resubmission and point to My orders. Cart quantity edits and removal use the supplied PATCH/DELETE item endpoints; shown quantities always come from GET cart.

Request fields come from the user; address PATCH was confirmed in chat. Shop Management lives at `/dashboard/shop`. It shares the admin shell styling but has a distinct shop sidebar with Dashboard, Categories, Products and Orders. The bottom action returns to `/superadmin/dashboard`. Only ADMIN and SUPER_ADMIN sessions can access shop routes. The previous partner route redirects to this admin route.

Category management uses `/add-category` and `/categories`. `management/categories/EcommerceCategoryForm.jsx` creates categories, `EcommerceCategoryList.jsx` paginates them, and `EcommerceCategoryDetails.jsx` loads a selected category in a dialog. `src/util/ecommerceCategories.mjs` uses the shared authenticated client against `/admin/ecommerce/categories` and sends exactly `name`, `description` and numeric `sortOrder` on create. Category totals on the shop overview come from this endpoint. The overview catalog preview remains a demonstration; Orders uses the live admin order API.

The API response formats are not yet live-verified. Local verification uses `postman/simulations/ecommerce-categories.sim.yaml`; assumptions and evidence are in the adjacent context file. Subcategories are managed under the same Categories sidebar group at `/add-subcategory` and `/subcategories`. The form builds SELECT and BOOLEAN specification templates and sends only the supplied POST schema to `/admin/ecommerce/subcategories`. The list defaults to all categories and sends `categoryId` only when a parent is selected. Category options load every page of the category API. The subcategory table searches and paginates the loaded result set locally because backend search/pagination parameters were not supplied. Its specification fields expand in each row. Category-table search applies to the current page.

The shop overview lives at `/dashboard/shop`. Shop sidebar pages use root-level URLs: `/add-category`, `/categories`, `/add-subcategory`, `/subcategories`, `/product-list` and `/orders`. Previous nested `/dashboard/shop/*` and `/superadmin/shop-*` URLs redirect to their matching canonical pages. All these routes require an admin session. The shared shop table header places the title on its own row and search/filter controls in the following row.

The Products sidebar parent contains Add Product (`/add-product`) and Product List (`/product-list`). Both require an admin session. Successful creation keeps Add Product open for image attachments and additional variants; Products List finishes the workflow. All Add Product inputs use MUI controls in a responsive three-column layout. These pages use `src/util/ecommerceProducts.mjs` through `MainApi`, whose base URL already includes `/api/v1`. The list sends `page`, `limit` and an optional `status`, defaulting to all statuses (the status parameter is omitted). Search applies to the current page. Add Product loads all category options and the selected category's subcategories, then renders SELECT/BOOLEAN specification controls from the subcategory template. Options and variants are editable; exactly one default, unique SKUs/combinations, whole paise prices, sale <= MRP and nonnegative whole stock are validated before posting. The initial product sends `images: []`. Select files with Choose image, then click Upload image. Uploaded assets are attached individually after creation returns the product ID. Product creation is not repeated if a later attachment fails.

View details performs GET `/admin/ecommerce/products/{ecommerceProductId}`. Publish uses POST `.../{ecommerceProductId}/publish` with confirmation. Stock received uses POST `/admin/ecommerce/variants/{ecommerceVariantId}/inventory-adjustments` with numeric positive `quantity`, `type: STOCK_RECEIVED` and `note`. Both actions refresh details; a successful write followed by a failed refresh is reported separately and requires reopening the product from Products List before further changes. No other inventory adjustment types were supplied. Publishing's POST method, `PUBLISHED` status, response wrappers and returned stock field names need live verification; no production writes were performed.

Product media uses multipart POST `/uploads/image` with only `purpose: ecommerce-product-media` and `file`. The shared Axios client removes its JSON content type for FormData. Upload responses reuse the existing application's raw/image/file/upload/cloudinary URL and public ID envelope support; both values must be present. POST `/admin/ecommerce/products/{id}/images` sends exactly `url`, `publicId`, `altText`, and numeric `sortOrder`. Image descriptions are generated from filenames, and compact previews sit beside the upload control. Sort order is editable before attachment; failed attachments retain uploaded values for retry with Upload image. Unsaved previews have a top-right X to remove them. The upload button shows a spinner throughout upload and attachment. Attached images have no remove action because no delete API was supplied. After draft creation, the separate Upload image button uploads and attaches selected images.

After creation, Add product variant posts to `/admin/ecommerce/products/{id}/variants` with only `sku`, `optionValues`, numeric `mrpAmountPaise`, `saleAmountPaise`, and `initialStock`. It validates against the saved option definitions and variant SKUs/combinations. The initial create still includes its variants array; subsequent variants use the dedicated endpoint and omit `isDefault`. Upload and attachment/variant writes are checked against local mocks; live upload responses and backend limits remain unverified.

Product row actions include View details and Edit product. Edit opens `/product-list/edit/{productId}`, protected by the existing `/product-list/:path*` admin matcher. It loads GET `/admin/ecommerce/products/{id}` to prefill category, subcategory, title, brand, GST, description, specifications and option definitions. Base product information is editable using the product PATCH contract supplied on 2026-11-15. Variant sale price and availability continue to use the separate variant endpoint. Each existing variant has editable saleAmountPaise and isActive controls, saved using PATCH `/admin/ecommerce/variants/{variantId}` with exactly those two fields. PATCH is an inferred method and still needs live confirmation; no production writes were made. Existing images and additional variants use the previously supplied attachment/variant endpoints.

Product List also displays Created date, Price, Variants and Stock. Values come from the list row and its returned variant data; unknown stock and prices remain unavailable rather than being presented as zero. Color/Colour options use a MUI popover with named swatches, a native input type=color picker and hex input. Existing color names are preserved in the API payload; custom colors are hex strings. Variant color selection is restricted to the saved option values.


Inventory Management contains Inventory List (`/inventory`) and Low-stock Variants (`/low-stock-variants`). GET `/admin/ecommerce/inventory` sends page and limit, defaulting to 1 and 20; the low-stock page adds only `lowStockOnly: true`. Search applies to the current page. The history table shows date, type, quantity, stock before/after, note and recorded-by name when supplied. Inventory and Low-stock Variants show a Low-stock threshold column. Inputs reject blank, negative, fractional and unsafe integer values. A spinner runs until completion; failures keep the entered value in the dialog. Order payment (2026-11-16): `/shop/orders/{orderId}` and the reused user order details show payment choices for pending, unpaid, unexpired orders. Select Razorpay and proceed to POST `/shop/orders/{orderId}/payment`, open Razorpay Standard Checkout, POST the three callback fields to `/shop/payments/{ecommercePaymentId}/verify`, then reload GET order. Payment creation sends `{}` because only its POST method and path were supplied; no frontend total is sent. The backend creation body and response have not been verified live. The parser accepts `payment.id` or `ecommercePaymentId`/`paymentId`, `razorpayOrderId`/`providerOrderId`, `amountPaise` and `currency`, plus public `keyId`/`razorpayKeyId`; `checkoutOptions`/`razorpay` and `razorpayOrder` envelopes are also supported. A missing public key can be configured with `NEXT_PUBLIC_RAZORPAY_KEY_ID`; never configure a key secret in the frontend. Missing payment references, amount, currency or key stop Checkout with a visible error.

Cash on Delivery is displayed as unavailable because no COD request or confirmation contract was supplied. It does not send an invented COD payload or mark an order paid. Failed or cancelled Razorpay Checkout is not verification success. Callback failures and ambiguous creation responses block another payment attempt in the mounted page; order status can be refreshed. The backend remains responsible for cross-reload idempotency, signature validation, payment capture and authoritative order status. Reference: https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/ .

Paid/captured/authorized/refunded payments, cancelled/expired/returned/completed orders, expired reservations and explicit server canPay=false remain blocked.
